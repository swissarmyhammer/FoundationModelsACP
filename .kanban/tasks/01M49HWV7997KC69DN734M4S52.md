title: Add ClientSideConnection.afterRespondingToCurrentRequest
---
## Why

FoundationModelsACPClient (task 3p0m0c1 on that board) must give `SessionModel` an async `selectPermission` and an async `cancelPermission`. Each must return only after the connection writes the `session/request_permission` response frame to the transport. Now a `Client` handler cannot know when the connection writes that frame. Thus a `session/prompt` that the caller sends just after the answer can go out before the permission response. Requested by the foundationmodelsacpclient-60 session (it replaces its upstream task qcdqcm3).

## What exists

- `Sources/FoundationModelsACP/Connection/Connection.swift`:
  - `final class ResponseHooks` (line 21) keeps `[Work]` in a `Mutex<Phase>`. `append(_:)` (line 74) drops a late closure and logs a warning. `runAll()` (line 92) runs the closures. `discardAll()` (line 101) releases them and does not run them.
  - `@TaskLocal static var currentResponseHooks: ResponseHooks?` (line 144).
  - `dispatchRequest(id:method:params:batchToken:)` (line 788) binds the hooks around the handler call. Then, when `completeInbound(...)` returns `true`, it calls `hooks.runAll()`. Otherwise it calls `hooks.discardAll()` (lines 822–826).
- `Sources/FoundationModelsACP/Connection/AgentSideConnection.swift`: `public func afterRespondingToCurrentRequest(_ work: @escaping @Sendable () async -> Void)` (line 263) only calls `Connection.currentResponseHooks?.append(work)`. A call outside an inbound request drops `work` and gives no signal.
- `Sources/FoundationModelsACP/Connection/ClientSideConnection.swift`: `serve(_:params:to:)` (line 175) calls `client.requestPermission` and `client.createElicitation` directly on the dispatch task. Thus the task-local is in scope in a `Client` handler. `ClientSideConnection` has no `afterRespondingToCurrentRequest` method.

## What

Final API (the same form on the two sides):

```swift
// AgentSideConnection and ClientSideConnection
public func afterRespondingToCurrentRequest(_ work: @escaping @Sendable () async -> Void)
public func afterRespondingToCurrentRequest(
    _ work: @escaping @Sendable () async -> Void,
    onDiscard: @escaping @Sendable () -> Void
)
```

Contract of `onDiscard`: the connection calls `onDiscard` exactly one time when `work` will never run, and never when `work` runs. Thus a caller that waits on `work` with a continuation can resume it from `onDiscard` and never stays suspended. `onDiscard` is synchronous, because `discardAll()` and `append(_:)` are synchronous. The cases:

1. The connection closed before it wrote the response (`discardAll()`).
2. The call comes after the hooks ran or were discarded (a late `append`).
3. The call comes outside an inbound request (no `currentResponseHooks`). Then `work` does not run, and `onDiscard` runs at once, before the method returns.

Approach:

1. `Connection.swift`: change `ResponseHooks` to keep entries of `work` and an optional `onDiscard`. Add `append(_ work: @escaping Work, onDiscard: (@Sendable () -> Void)?)`, and keep `append(_:)` as a call with `onDiscard: nil`. `discardAll()` calls each `onDiscard` in registration order, outside the lock. A late `append` logs the warning that exists now, then calls `onDiscard` outside the lock. Update the type doc comment: it names only the agent-side entry point now.
2. `Connection.swift`: add one shared helper, for example `static func deferAfterCurrentResponse(_ work:, onDiscard:)` in the `extension Connection` with `currentResponseHooks`. When there are no hooks, it calls `onDiscard` at once.
3. `AgentSideConnection.swift`: add the `onDiscard:` overload. Keep the signature of the method that exists now, and make it call the helper with no `onDiscard`. Document `onDiscard` in the doc comment.
4. `ClientSideConnection.swift`: add the two methods in a new `// MARK: - Deferred post-response work` section. The doc comment names `requestPermission(_:)` and `createElicitation(_:)` as the handlers to follow, and gives the same contract as the agent side.
