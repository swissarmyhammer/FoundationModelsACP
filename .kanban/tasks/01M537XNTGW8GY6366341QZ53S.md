Elicitation plan section 10, rule R2, group A.

Defect: in Connection.request, the frame write and cancelOutbound are two separate tasks on the actor, with no fixed order. write(_:failing:) does not check that the request is still pending. Also, two transport writes can overlap, so a cancel that is written during the request write can reach the wire first. Result: the $/cancel_request can go out before its request. The peer drops it (unknown id), then shows the request, and nothing ever ends it.

Fix (decision): both halves of the rule, with a state for each request frame write.
- Cancel before the write starts: the connection writes neither the request nor the $/cancel_request. The caller gets CancellationError. Reason: the peer never sees a question that is already ended, so a client shows no question. This is better than "request, then cancel", where the client shows a question and then removes it.
- Cancel while the write is in progress: the connection writes the $/cancel_request only after the request write returns. Reason: ACPTransport lets two writes overlap, so only a wait for the write to end gives a fixed order.
- Cancel after the write: no change.

Test: an internal scheduler seam on Connection lets the test run the write work and the cancel work in a fixed order. A transport holds the request write until the test releases it. The tests must fail before the fix.
